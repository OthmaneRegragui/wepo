# Architecture

## Overview

Wepo Office is a static single-page application. The browser is the whole
runtime: there is no application server, no document service, and no database.
The production artifact is a directory of HTML, CSS, JavaScript, WebAssembly,
fonts, and sample files.

```
Browser tab
  React UI (apps/web)
    dashboard, landing pages, editor shell, SEO
        |
        +-- lazy editor wrapper (Word / Sheets / Slides)
        |      |
        |      +-- BetterOffice WebAssembly engine (worker)
        |             open / edit / save / print display list
        |
        +-- @wepo/core
               detection, ZIP audit, file loading, IndexedDB,
               output naming, download / File System Access
```

## Repository layout

```

  public/                static assets served as-is
    _headers             Cloudflare Pages security headers and CSP
    _redirects           SPA fallback

    licenses/            bundled license notices (generated)
    samples/             real DOCX/XLSX/PPTX test files (generated)
    templates/           blank DOCX/XLSX/PPTX files (generated)
  src/
    components/          shared UI, layout, file picker, toasts
    editors/             isolated Word, Sheets, and Slides wrappers
    hooks/               document launcher and recent documents
    lib/                 app metadata, CSV, fonts, print, SEO, utilities
    pages/               dashboard, app landing, editors, legal pages
    stores/              Zustand document handoff and toast state
packages/core            framework-free document safety and storage layer
scripts/                 font copy and sample/template generators
tests/unit               Vitest unit tests
tests/e2e                Playwright browser tests
```

## Editor isolation

Each editor is a separate lazy chunk and a separate component:

- `WordEditor` wraps `DocxEditor` and exposes `save()` and `print()`.
- `SheetsEditor` wraps `XlsxEditor` and exposes `save()`, `print()`, and
  `exportCsv()`.
- `SlidesEditor` wraps `PptxEditor` and exposes `save()` and `print()`.

The editor page owns the shell: document name, dirty indicator, save/export
buttons, recovery state, and the error boundary. Editors receive the file bytes
and report readiness through an `EditorBridge`. The shell never reaches into
engine internals.

This isolation means an engine failure is contained by a React error boundary,
and opening a spreadsheet does not download the presentation engine.

## Data flow

### Opening a file

1. `OpenFileButton` or `FileDropZone` receives a browser `File`.
2. `loadLocalFile()` checks size, extension, MIME-independent magic bytes, and
   the ZIP structure.
3. A CSV is converted to XLSX in-browser with SheetJS so the workbook engine
   can edit it. The original CSV is untouched.
4. The bytes are written to IndexedDB as a recovery copy (when under the
   50 MB per-document cap) and handed to the editor route in memory.
5. The editor route opens the requested engine chunk, which loads WebAssembly
   in a worker.

### Editing and saving

- Engine document-change events mark the session dirty.
- A 30-second debounce and a `pagehide` handler write a fresh recovery snapshot
  to IndexedDB.
- Explicit Save calls the engine to serialize a new file, then uses the File
  System Access picker when available, otherwise a normal download.
- Output names use `buildOutputName()`, which adds an `-edited` or `-export`
  suffix. The source file is never overwritten.
- Recovery writes are local only; they are not an external save.

### Printing and PDF

- Word delegates to the DOCX engine's print/print-preview path.
- Sheets asks the engine for a display list per visible worksheet, paints the
  list to a canvas, and prints the images through a hidden iframe.
- Slides lays out each slide, paints it to a canvas, and prints the images
  through the same iframe. Pictures are omitted by this print path; PPTX
  export keeps them.

The browser print dialog is the PDF path. No PDF is uploaded or generated by a
remote service.

## Core safety layer (`packages/core`)

### Detection

`detectFile()` combines the file extension with magic bytes. The extension
chooses the editor; the signature verifies that the bytes are a plausible
container. ZIP-based OOXML files must start with a ZIP signature. A mismatch is
rejected before the engine is called.

Only DOCX, XLSX, CSV, and PPTX are openable. Legacy and OpenDocument formats
return an explicit message telling the user to re-save as OOXML.

### ZIP audit

`auditZip()` parses the ZIP central directory without decompressing. It rejects:

- missing or corrupt central directories,
- ZIP64 archives,
- more than 5,000 entries,
- more than 500 MB of uncompressed content,
- entries larger than 150 MB,
- compression ratios above 200:1 for entries above 1 MB,
- encrypted entries,
- compression methods other than store and deflate.

These checks reduce decompression-bomb and malformed-container risk before an
engine receives the bytes. They are a mitigation, not a formal proof of safety.

### Storage

IndexedDB database `wepo-office` stores document metadata and recovery bytes.
The policy keeps at most 25 documents and 300 MB total, and skips byte storage
for documents above 50 MB. When IndexedDB is unavailable, the app still opens
the document in memory and tells the user that recovery is unavailable.

### Download and naming

`saveBytesAs()` prefers `showSaveFilePicker()` and falls back to an anchor
download. It returns `saved`, `downloaded`, or `cancelled` so the UI can report
what happened. `sanitizeFileName()` strips path separators and control
characters.

## UI and state

- React 19 with React Router.
- Zustand stores for the in-memory document handoff and toast notifications.
- Tailwind CSS for layout and color-coded app accents: Word blue, Sheets
  green, Slides orange.
- Editors are React.lazy chunks with Suspense fallbacks.
- The dashboard and app landing pages share the file drop zone and launcher.

## SEO

`useSeo()` updates the title, description, canonical link, Open Graph image,
robots meta tag, and JSON-LD in the document head. The dashboard, each app
landing page, privacy, licenses, and compatibility pages have their own metadata.
Static `robots.txt`, `sitemap.xml`, `site.webmanifest`, `favicon.svg`, and
`og-image.svg` ship in `public/`.

## Security and privacy

- Static hosting only; no upload endpoint exists in the application.
- No analytics or tracking of document contents or filenames.
- Strict Content Security Policy in `public/_headers`.
- COOP `same-origin`, COEP `require-corp` (needed for SharedArrayBuffer), and
  CORP `same-origin`.
- `X-Content-Type-Options: nosniff`, `X-Frame-Options: SAMEORIGIN`,
  `Referrer-Policy: strict-origin-when-cross-origin`.
- Permissions policy disables camera, microphone, geolocation, payment, and USB.
- File validation runs before engine invocation.
- The app never claims unsupported formats or features are supported.

The CSP allows `wasm-unsafe-eval` because the engines compile WebAssembly.
Styles require inline styles for the engines. Workers and blobs are limited to
same-origin or blob URLs.

## Static deployment

The reference target is Cloudflare Pages:

- Build command: `npm run build`
- Output directory: `apps/web/dist`
- `_headers` supplies the security and cross-origin isolation headers.
- `_redirects` supplies the SPA fallback.

Any static host works if it can serve the same headers. Without COOP/COEP,
`SharedArrayBuffer` is unavailable and the worker-based Sheets editor may fall
back or fail; this is a hosting requirement, not a backend dependency.

## Testing strategy

- Unit tests (Vitest) cover detection, ZIP checks, file loading, CSV
  conversion, download fallback, output naming, and storage-unavailable paths.
- E2E tests (Playwright) cover the dashboard and landing pages, opening real
  sample files, a formula edit, CSV export, save downloads, slide creation, and
  unsupported-file errors.
- Manual compatibility testing uses real files from Microsoft Office,
  LibreOffice, and Google Workspace; results are recorded in
  `COMPATIBILITY.md`.

The test environment forces the download fallback by removing
`showSaveFilePicker`, so save behavior is deterministic in headless Chromium.
